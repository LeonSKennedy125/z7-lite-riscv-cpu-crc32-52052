# 提示词模板：从接口描述生成契约、测试与负对照

> 用法：把尖括号 `<...>` 替换成你的外设/软核信息，整段发给编码智能体。要求它先输出契约表，再写测试；不要直接让模型“生成一个外设”。

```text
你是数字设计验证工程师。下面是一个 <总线类型：同步 valid/ready MMIO / AXI4-Lite / 其他>
外设的接口描述。请先不要写 RTL，按以下顺序输出：

1. 契约表：每个寄存器的地址、方向、位宽、读写副作用、完成条件、错误条件、复位值。
   对每个副作用写清“唯一发生时刻”；对 ready 写清它依赖哪些寄存状态，是否可能依赖 valid/地址/CPU 控制信号。
2. 边界表：BUSY 写配置、重复 START、ABORT 与 START 同周期、长度 0、尾部不足一个字、
   未完成请求撤回、复位/中止放弃任务、COMMIT 后写入、非法地址/方向/字节使能。
3. 自检测试清单：每条测试的激励、必须观察的内部/外部事件、期望结果；
   正常功能与“预期错误注入”分开标记，不能混为一个 PASS。
4. 主机解析器负对照：至少 9 类（截断、多余、最后一项错误、未知 magic/version、
   非零错误计数、零周期、会话周期大于完整周期、重复 case id、错误字节序）。
5. 独立参考：说明 golden 由什么独立工具/标准向量产生；禁止由 DUT 反推。
6. 证据清单：输入哈希、工具版本、实际 argv、退出码、stdout/stderr、失败 attempt 保留位置。

外设描述：
<粘贴接口/寄存器/时序描述>

约束：
- 不添加描述中没有的功能；
- 不把仿真结果标成上板；
- 不删除失败或放宽正确期望；
- 如果信息不足，先列缺口，不猜。
```

## 输出验收

- 契约表能直接映射到 RTL 的 always/assign 和测试台的采样点。
- 每条副作用只有一个发生时刻。
- `ready` 不形成 `valid → ready → CPU 等待 → valid` 的组合环。
- 负对照能实际拒绝错误输入，而不是只打印“通过”。
- 独立参考与 DUT 实现语言/工具不同源。
